COUCHE 02

L’adaptateur natif

Fenêtres Win32, messages, focus et services. Le worker MTA possède les objets GSMTC ; une boîte bornée transmet des snapshots Rust à l’UI. Le lanceur utilise un worker STA paresseux.

Entrée utilisateur / événement Windows↓État métier → géométrie → surface↓Rendu seulement si nécessaire

Dépendances : app → windows ; windows → ui et core ; ui → core. Les flèches décrivent les couches, pas quatre threads séparés.

01

Une fenêtre, pas un navigateur

Une fenêtre Win32 flottante et layered, sans AppBar ni réservation de bureau. Le rendu combine une surface BGRA, du texte GDI et UpdateLayeredWindow. Les coins arrondis sont dessinés dans les pixels, avec transparence hors de la forme.

crates/island-windows/src/surface.rs ↗
02

L’animation a une fin

La transition utilise t²(3−2t), avec une durée adaptée à la distance restante. Le timer de rendu est temporaire. Répéter Échap ne prolonge pas la fermeture. La réduction des animations produit un changement immédiat.

crates/island-core/src/lib.rs · Transition ↗
03

Windows comme source multimédia

GSMTC expose les sessions des lecteurs compatibles. Le worker WinRT MTA écoute les événements, borne ses données et invalide les résultats périmés. Le thread UI ne possède pas ces objets COM. Aucun scraping de navigateur.

crates/island-windows/src/media.rs ↗
04

Le focus se mérite

L’ouverture explicite peut demander le focus. La désactivation et les clics extérieurs replient sans réactiver de force une autre fenêtre. Les raccourcis optionnels utilisent RegisterHotKey ; aucun hook clavier global.

crates/island-windows/src/lib.rs ↗
05

Dormir quand rien ne change

La boucle UI attend les messages Windows. Les préférences sont écrites par un writer coalescé ; les workers attendent leurs événements. Le minuteur caché se réveille à son échéance, pas chaque seconde. Cela ne constitue pas une garantie de CPU ou de GPU absolument nul.

crates/island-core/src/timer.rs · Timer::next_wake ↗
06

Des ressources avec une durée de vie

Abonnements, timers, capture, hooks temporaires, surfaces et polices sont libérés à l’arrêt. Rust aide à structurer cette propriété ; les chemins unsafe et les appels Windows bloquants restent des responsabilités explicites.

Deux environnements.
Des rôles distincts.

APPLICATION NATIVE

Rust · Win32 · WinRT

Rust pour les règles et la propriété des ressources. windows-sys 0.61.2 pour Win32, windows 0.62.2 et windows-future 0.3.2 pour les projections WinRT. GDI/BGRA pour une surface légère, GSMTC pour les lecteurs compatibles.

Limites : API Windows uniquement, accessibilité du panneau sans fournisseur UI Automation, fournisseurs multimédias variables.

CE SITE

Next.js · React · TypeScript

Pages exportées en statique, composants interactifs côté navigateur et CSS local. Le code Rust est extrait au build. Le moteur de démonstration traduit des contrats précis ; il ne compile ni n’exécute l’application native.

Pas de serveur applicatif, compte ou service externe. Coloration lexicale légère, sans Shiki, Motion, Tailwind ni MDX supplémentaires.

Ce que l’on peut affirmer.

Les campagnes documentées rapportent 67 tests Rust réussis sur le socle P6. Ce n’est pas une nouvelle mesure réalisée par le site. Le banc P4 conserve un résultat brut de 32/33 ; DPI dynamique, multi-écrans, jeux exclusifs et endurance restent à certifier.
